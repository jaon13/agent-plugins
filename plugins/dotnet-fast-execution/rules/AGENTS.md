# Fast .NET Execution & Multi-Agent Rules

Always enforce these execution rules across direct turns, `swarm`, `teamwork`, `/boost`, `/goal`, and subagents:

1. **Ownership & Pipeline**: Verify both UI (WPF/XAML) and non-UI `.NET` edits end-to-end inside Antigravity. For feature or multi-file `.NET` work, load and follow skills under `~/.gemini/config/skills/` on demand: `brief-refine` → `codebase-map` → `arch-blueprint` → implement → `code-consistency` → `stabilize-gate` (plus `dotnet-xray` / `graph-engineering`).
2. **Index-First Lightweight Navigation**:
   - For routine discovery and simple edits, prefer `python "$HOME/.agents/bin/xray_run.py" xray-index` (`slice`, `search`, `deps`, `partials` against `<repo>/.xray/index.db`) or 1–2 targeted `rg` calls (when the file/symbol is already known), followed by targeted `read_file` ranges (`StartLine`/`EndLine`, `<150` lines).
   - Avoid chaining multiple `code-xray` MCP calls for simple tasks (lazy schema reads + MSBuildWorkspace add analysis overhead). When using `code-xray`, prefer `.xray/index.db`-backed tools (`get_feature_slice`, `get_partial_clusters`, `get_architecture_links`, `get_type_overview` with default `preferSemantic=false`); reserve heavy Roslyn semantic tools (`find_callers`, `find_implementations`, `get_symbol_blast_radius`, `search_reusable_apis`, `find_structural_clones`) for interface/virtual call-site verification or multi-file refactoring.
3. **Fast .NET Inner-Loop Builds & Tests**:
   - Build only affected `.csproj` files during iteration with `-p:FastBuild=true --no-restore` (when `FastBuild` is supported, otherwise `--no-restore`). Upper-app builds pulling `>= 3` external shared dependencies (configured via `~/.agents/locks/config.json`) MUST pass `--no-dependencies` (or `-p:BuildProjectReferences=false`, or `--no-build` for test-only runs) to avoid `ProjectLock` `DEP_GUARD_DENIED`.
   - Run filtered tests first: use `dotnet vstest <TestDllPath> --TestCaseFilter:...` when VSTest runs under an ancestor MTP `global.json`, and run compiled xUnit v3 executables (`<Project>.Tests.exe` with `-class` / `-trait`) directly when supported.
   - Reserve `-p:FastBuild=false` rebuilds, full test suites, and `python "$HOME/.agents/bin/xray_run.py" verify_dotnet.py` / `check_consistency.py` once for the final gate. Because `ProjectLock` enforces a strict **4-module session cap** (`LIMIT_DENIED`, no `.slnx` exemption), solutions exceeding 4 modules must shard even final rebuilds/tests per affected `.csproj` or batch them in groups of `<= 4` modules per turn/worker rather than locking `> 4` modules at once.
4. **Zero Polling**: NEVER call `manage_task` or `read_board` in polling loops or run shell sleep waits. End your turn (or call `swarm_wait` in swarms) so reactive completion notifications wake you.
5. **Multi-Agent Worker Brief Injection & Sharding**:
   - Subagents, `swarm` workers, and `teamwork` workers start fresh without parent context. Coordinators MUST inject Rules 2–4, `code-xray` usage, and exact relevant `SKILL.md` paths verbatim into every `swarm` brief, `teamwork` prompt, `DISPATCH.md`, and `invoke_subagent` prompt.
   - Before spawning writers on shared/multi-module workspaces, check `python "$HOME/.gemini/config/plugins/project-lock/scripts/project_lock.py" status`, pre-claim disjoint module slices per worker (`project_lock.py claim --conv-id <worker-id> --modules <mod1,mod2>`), and release on worker completion/kill (`project_lock.py release --conv-id <worker-id>`).
   - Shard bulk refactors touching `>10–15` files or `>4` modules by architectural layer or `.csproj` into non-overlapping worker slices (`<= 4` modules per worker/turn, ideally `1–2` modules) so parallel writers never contend on the same files, MSBuild locks, or `ProjectLock`'s 4-lock cap; ensure upper-app builds with `>= 3` shared dependencies pass `--no-dependencies` (or `-p:BuildProjectReferences=false`).
